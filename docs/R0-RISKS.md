# R0 — первые замеры Linux

Дата: 27 октября 2026. **R0 ещё не завершён.** Ниже — реально выполненные
короткие проверки на машине разработки. Часовой прогон, физическое
переподключение USB-гарнитуры и слабый ПК остаются обязательными.

## Что создано

`tools/EliteRec.Probe` — консольный стенд .NET 10. В отличие от будущего
приложения, не имеет интерфейса и не сохраняет звук микрофона. Режимы:

- `devices` — имена и описания устройств, системный вход/выход;
- `capture` — два независимых record-stream libpulse: микрофон и монитор
  выбранного вывода, float32 mono 48 кГц, запрос фрагмента 20 мс;
- `encode` — синтетический сигнал, общий микс MP3 mono 128 кбит/с и
  раздельные каналы MP3 stereo 192 кбит/с, quality 2, CBR, обычный stereo.

Native-вызовы и threaded mainloop адаптированы из
`Linux EliteSip/src/EliteSIP.Audio.Pulse`. Ожидание подключения и готовности
ограничено 5 с. Потоки R0 открываются с `PA_STREAM_DONT_MOVE`: исчезновение
источника должно быть видно как отказ, а не скрытая подмена. Восстановление
и переключение на запасное устройство относятся к R4.

`scripts/r0-monitor-smoke.py` создаёт временный null-sink, проигрывает в него
синтетический тон, проверяет захват монитора и отказ при исчезновении источника,
после чего удаляет своё устройство. Тон не направляется в колонки/гарнитуру.
Системную громкость скрипт не меняет. Сам звуковой сервер должен быть доступен
из пользовательской сессии.

## Условия замеров

| Параметр | Значение |
|---|---|
| ОС разработки | Linux Mint 22.3, x64; это **не** целевая Debian 13 |
| CPU | Intel Core i7-10750H, 6 ядер / 12 потоков |
| RAM | 7803 МиБ, около 8 ГБ |
| Носитель рабочего каталога | SSD |
| SDK / runtime | .NET SDK 10.0.402 / runtime 10.0.13 |
| Аудиосервер | PulseAudio API на PipeWire 1.0.5 |
| Устройство | USB Microsoft LifeChat LX-3000, C-Media |
| Кодеки в системе | libmp3lame.so.0, libFLAC.so.12, libopus.so.0 |

Параметры окружения и маршрутов не менялись для основного 20-секундного замера.
Виртуальный вывод использовался только в отдельной проверке тестового сигнала.

## Результаты

### Два потока, 20 секунд

Исходные данные: [dev-capture.json](r0-results/dev-capture.json).

| Метрика | Микрофон | Системный монитор |
|---|---:|---:|
| Доставлено отсчётов | 960960 | 961920 |
| Дыр / переполнений / ошибок чтения | 0 / 0 / 0 | 0 / 0 / 0 |
| Пик (линейный, 1 = full scale) | 0,13675 | 0 |
| Отсчётов с уровнем ≥ 1 | 0 | 0 |
| p95 интервала обратного вызова | 21,61 мс | 21,51 мс |
| Максимальный интервал обратного вызова | 32,05 мс | 32,12 мс |

Системный монитор в этом прогоне молчал. Поэтому сам факт получения отсчётов
не принят за подтверждение захвата звука: выполнен отдельный тест с тоном.

### Монитор и исчезновение источника

Исходные данные: [dev-monitor.json](r0-results/dev-monitor.json) и
[dev-disconnect.json](r0-results/dev-disconnect.json).

- Синус 440 Гц, 16-bit PCM, 48 кГц, амплитуда 8000/32768, подан в null-sink.
- Монитор дал пик **0,244140625**, ожидаемый для этого сигнала; ошибок и
  переполнений нет. Реальный микрофон продолжал захватываться независимо.
- Удаление виртуального источника во время захвата обнаружено; стенд сохранил
  причину и накопленные измерения, завершился с кодом **3**, без зависания.
- Это проверка реакции libpulse на исчезновение узла, **не** проверка физического
  USB hotplug, смены профиля Bluetooth или продуктового fallback.

### Кодирование двух MP3

Исходные данные: [dev-encode.json](r0-results/dev-encode.json).

| Метрика | Результат |
|---|---:|
| Длительность входа для каждого файла | 120 с |
| Реальное время генерации, кодирования и сброса обоих файлов на диск | 2,573 с |
| CPU процесса | 2,565 с |
| CPU относительно длительности аудио, в долях одного ядра | 2,137% |
| Скорость относительно реального времени | 46,64× |
| Пиковый working set процесса | 41984000 байт (~40 МиБ) |
| Микс | 1920384 байт, 5001 кадр, MONO, 128 кбит/с, 48 кГц |
| Раздельные каналы | 2880576 байт, 5001 кадр, STEREO, 192 кбит/с, 48 кГц |

Проверены заголовки **всех** кадров обоих файлов, включая отсутствие joint
stereo. Полезная длительность входа — 120 с; дополнительный MP3-кадр связан
с буферизацией кодера. Декодирование и проверка разделения голосов здесь
не выполнялись. Синтетический сигнал не заменяет нагрузочный тест речи;
слабый ПК, HDD и одновременный продуктовый захват/микширование ещё не измерены.

### Тайминги и дрейф

Потоки стартуют последовательно. Для наклона отбрасываются первые 3 с,
постоянное смещение старта исключается линейной регрессией. В JSON раздельно
сохраняются число доставленных отсчётов, время `pa_stream_get_time` и задержка.

За короткий прогон изменение разницы доставленных отсчётов составило 20 мс.
Расчётные относительные наклоны составили −70,12 ppm по доставленным отсчётам
и +904,31 ppm по серверному времени. **Эти числа не являются оценкой физического
дрейфа устройств:** они содержат квантование по фрагментам, начальную адаптацию
PipeWire и джиттер наблюдения. Их нельзя экстраполировать как результат за час.

Вывод для R2: нельзя просто склеивать очередные блоки обоих источников по
порядку прихода. Нужны общая временная шкала, учёт задержек и ограниченная
компенсация заполнения буферов. Конкретный алгоритм пока **не выбран**.
Приёмку ≤ 50 мс за 60 минут нужно проверять по общему тестовому сигналу
на обоих каналах готового тракта, а не только по счётчикам API.

## Воспроизведение

Из корня репозитория, в обычной пользовательской аудиосессии:

```bash
dotnet restore EliteRec.Linux.slnx
dotnet build EliteRec.Linux.slnx -c Release --no-restore
dotnet test EliteRec.Linux.slnx -c Release --no-build --no-restore

dotnet tools/EliteRec.Probe/bin/Release/net10.0/EliteRec.Probe.dll devices
dotnet tools/EliteRec.Probe/bin/Release/net10.0/EliteRec.Probe.dll capture --seconds 20 --output artifacts/r0/capture-new.json
dotnet tools/EliteRec.Probe/bin/Release/net10.0/EliteRec.Probe.dll encode --seconds 120 --output artifacts/r0/encode-new
python3 scripts/r0-monitor-smoke.py

# Следующий обязательный замер, НЕ выполнен на момент этого отчёта:
dotnet tools/EliteRec.Probe/bin/Release/net10.0/EliteRec.Probe.dll capture --seconds 3600 --output artifacts/r0/hour-new.json
```

Выходной файл/каталог должен быть новым: чужие результаты не перезаписываются.
Для `devices`/`capture` нужен `pactl` из `pulseaudio-utils`; smoke-скрипту нужен
также `paplay`. Для кодирования — `libmp3lame0`; ffmpeg не используется.
Стенд не выбирает устройства по номеру: `--source` — имя source, `--sink` — имя
sink. Имена можно получить в `devices`.

В Codex sandbox аудиосокет и локальный сокет VSTest недоступны; живые замеры
и тесты выполнены с разрешением запуска вне песочницы. Обычная Release-сборка
в песочнице проходит с `-m:1 -nr:false`. Локальное восстановление выполнено
с `-p:NuGetAudit=false`; аудит NuGet при этом не проводился.

13 тестов прошли: известный наклон часов, исключение прогрева и коротких
наблюдений, статистика, невалидные параметры, реальное кодирование libmp3lame
и проверка MP3-заголовков/повреждённых файлов. Native-тесты требуют libmp3lame0.
Добавлен workflow сборки и тестов; удалённый запуск CI пока не выполнялся.

## Что осталось для завершения R0

- Сравнение независимых физических часов микрофона и вывода, не только одной
  USB-карты. Часовой прогон виртуальных источников на машине разработки
  выполнен в R2: сдвиг ≤ 14,188 мс, без потерь; [результаты](R2-AUDIO.md).
- Реальное отключение и возврат USB-гарнитуры с фиксацией маршрута и времени.
- Те же замеры на A6 / 4 ГБ / HDD и на целевой EliteLinux (Debian 13).
- Акустическая проверка синхронизации физических устройств. WAV-тракт и
  программная синхронизация реализованы в R2.

Наличие этого документа само по себе **не закрывает R0**. R1 и программная
приёмка R2 выполнены с сохранением аппаратных проверок R0 в списке.

## Первичные источники API

- [PulseAudio async API](https://www.freedesktop.org/software/pulseaudio/doxygen/async.html)
  и исходники EliteSIP на локальном диске — схема контекста/потоков.
- [LAME include/lame.h](https://github.com/lameproject/lame/blob/master/include/lame.h) —
  режимы MONO/STEREO, буферы и нормализованный float-вход
  `lame_encode_buffer_ieee_float`.
