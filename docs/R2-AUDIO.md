# R2 — захват, синхронизация и WAV

27 октября 2026. **R2 принят на виртуальных источниках машины разработки.**
Реальный часовой прогон завершён: 3596 маркеров, максимальное расхождение
14,188 мс при допуске 50 мс, пропусков и переполнений нет.
Аппаратные проверки R0/R4 остаются открытыми.

## Что работает

- Два независимых record-stream libpulse: выбранный микрофон и monitor-source
  выбранного вывода. Формат захвата — mono float32, 48 кГц; системное стерео
  сводится в моно аудиосервером.
- Общий монотонный таймлайн, оценка скорости часов каждого источника,
  плавная компенсация рассогласования, ограниченные кольцевые буферы.
- Два PCM16 WAV на 48 кГц: общий моно-микс и стерео, L=микрофон, R=система.
- Ручные запись / пауза / продолжение / стоп, таймер и живые уровни в окне.
  Пауза не сохраняется как тишина: оба потока продолжают читаться.
- Закрытие окна завершает текущие WAV перед остановкой сессии.
- При отключении источника — явная ошибка и закрытие файлов, без зависания.
  Автоматическое переключение и возвращение устройств относятся к R4.

Кодирование MP3/FLAC/Opus и восстановление после kill/power loss — R3.
В этом этапе запись идёт в WAV. Трей, горячая клавиша, история «бабочки» и
полный сценарий сохранения с названием — R5; окно пока остаётся открытым.

## Границы модулей

| Модуль | Ответственность |
|---|---|
| `EliteRec.Core/Recording` | Модель состояния, контракты сессии/приёмника, ограниченные буферы, оценка часов, resampling и микс |
| `EliteRec.Audio.Pulse/PulseCaptureStream` | Native capture, метки времени, передача отсчётов в Core, счётчики ошибок |
| `EliteRec.Audio.Pulse/PulseRecordingSession` | Общий таймлайн, команды с временными границами, поток обработки и жизненный цикл |
| `EliteRec.Encoding/RecordingSink` | Пара файлов (в R2 — WAV; с R3 также MP3/FLAC, см. R3-ENCODING.md), предел RIFF и закрытие файлов |
| `EliteRec.App` | Предпрослушивание, состояния кнопок, уровни, сохранённый выбор устройств |
| `tools/EliteRec.Recorder` | Тот же продуктовый тракт без окна, воспроизведение диагностического журнала |

В native callback нет файлового I/O и кодирования. Обработка/запись выполняются
отдельным потоком. Смена выбранных устройств закрывает старый предпросмотр;
во время записи выбор заблокирован. До R4 активная запись сохраняет исходные
привязки устройств и не следует за новым системным default.

## Синхронизация

Начало каждой порции привязывается к общему `Stopwatch` по raw
`pa_timing_info`: времени измерения, read/write index и задержкам source/sink.
Для монитора учитывается момент воспроизведения вывода. Сглаженный UI-таймер
`pa_stream_get_time` не используется как точная метка аудио.

Для каждого канала хранятся последние 2 секунды отсчётов и до 64 опорных
точек с шагом не меньше 250 мс (окно примерно 16–17 с). Линейная регрессия
оценивает соответствие «общий момент времени → номер отсчёта». База недостаточна —
используется номинальная частота; оценка частоты ограничена ±1%.

Позиция чтения движется непрерывно: линейная интерполяция плюс ограниченная
плавная коррекция ошибки (не более ±0,5% сверх оценки частоты). Не вставляются
и не выбрасываются целые аудиоблоки ради выравнивания.

Выходные блоки — по 480 отсчётов, 10 мс, с начальным запасом 250 мс по времени.
**Одного таймера недостаточно:** блок обрабатывается только когда оба
буфера действительно содержат нужные отсчёты. Поздняя доставка задерживает
сохранение, а не заменяется вымышленной тишиной. Если источник не передаёт
данные больше 2 с — канал считается пропавшим (R4). Действительно потерянные
данные с R5 не обрывают запись: на их месте тишина и строка в файле событий
(до 28 октября 2026 потеря больше 100 мс завершала запись — на слабом ПК это
обрывало звонок, см. [R5-INTERFACE.md](R5-INTERFACE.md), «Нагрузка и подвисания»).

Микс — сумма 1:1 с мягким ограничителем выше 0,8 full scale. На старте и
границах паузы/стопа применяется рампа 5 мс. Переключателей усиления пока нет.
PCM16 преобразование ограничивает амплитуду до допустимой и заменяет NaN/Inf
нулём. RIFF-файл ограничен 4 ГБ; переполнение завершается явной ошибкой.

## Найденный сбой и регрессия

Первый длительный прогон остановился примерно на 9-й минуте. Ускоренный
сценарий — задержка только тестового процесса на 500 мс — дал тот же сбой
за несколько секунд, при нулевых дырках/переполнениях у сервера.

Сохранён журнал только метаданных (время/канал/число отсчётов, **без аудио**).
До исправления его повтор давал 5652 отсутствующих отсчёта, все — попытки
прочитать ещё не доставленное будущее; затирания кольцевого буфера не было.
Причина: записывающий поток продвигался по настенным часам, не проверяя
готовность обоих каналов после задержки планировщика.

Добавлен `TryRender`: при отсутствии будущих данных таймлайн остаётся на
месте до их получения. Тот же журнал теперь даёт 0 пропусков. Регрессионный
тест `DeliveryRegressionTests` до исправления падал с 5652, после проходит.
Временная сборка журнала из продуктового кода удалена; fixture и инструмент
повтора оставлены в tests/tools.

## Проверки на машине разработки

Окружение — то же, что в [R0-RISKS.md](R0-RISKS.md), Linux Mint / PipeWire,
не целевая EliteLinux. Автотесты используют виртуальные источники и
синтетический сигнал; реальная речь и реальные колонки не используются.

| Проверка | Результат |
|---|---|
| Обычная запись, 12 с | 12,00 с WAV, максимальный сдвиг 16,188 мс, пропусков/переполнений нет |
| 12 с, пауза 2 с | 10,00 с WAV, максимальный сдвиг 1,604 мс |
| После исправления: 20 с с задержками процесса по 500 мс | 20,01 с WAV, максимальный сдвиг 10,771 мс, пропусков/переполнений нет |
| Исчезновение виртуального источника | Процесс завершился с кодом 2, оба WAV читаемы и одинаковой длительности |
| Закрытие активной сессии без «Стоп» | Два корректных WAV по 8,00 с, состояние Closed, пропусков нет |
| Час моделируемых независимых часов | Пары +300/−250 ppm и −500/+400 ppm, ошибка < 50 мс |
| Сборка | Release, 0 предупреждений, 0 ошибок |
| Тесты | 43 прошли: 16 Core/Encoding, 8 App, 6 Pulse, 13 Probe |
| Реальная часовая запись после исправления | WAV 3599,98 с, 3596 маркеров, максимальный сдвиг 14,188 мс, все счётчики потерь/переполнений — 0 |

Час моделируемого времени не считается реальной часовой выдержкой. В живом
тесте оба источника виртуальные и работают на одном сервере; независимые
физические устройства и A6 / 4 ГБ / HDD ещё требуют проверки R0/R4.
Результаты: [r2-results](r2-results/), часовая проверка — [hour.json](r2-results/hour.json).

У консольного процесса на 57:32 средняя нагрузка — 4% одного ядра, RSS —
28 800 КиБ (около 28 МБ). Между замерами 40:21 и 57:32 RSS не изменился.
Это отдельные замеры `ps`, не пиковое потребление и не замер GUI;
результат не переносится на A6 без проверки. Данные:
[resources.json](r2-results/resources.json).

## Запуск

```bash
dotnet restore EliteRec.Linux.slnx
dotnet build EliteRec.Linux.slnx -c Release --no-restore
dotnet test EliteRec.Linux.slnx -c Release --no-build --no-restore
dotnet run --project src/EliteRec.App -c Release --no-build
```

Окно включает предпрослушивание для проверки звука. Файлы создаются только
после «Начать запись», в «Записи EliteRec» на рабочем столе. Имена содержат
местную дату/время и суффикс против совпадений; стереофайл имеет `_stereo`.
После «Стоп» имя сохранённого файла показано в окне.

Консольный вход требует явных имён source и monitor-source:

```bash
dotnet tools/EliteRec.Recorder/bin/Release/net10.0/EliteRec.Recorder.dll \
  --source SOURCE_NAME --system-source MONITOR_SOURCE_NAME \
  --seconds 20 --output artifacts/manual/recording

python3 scripts/r2-audio-smoke.py --seconds 20
python3 scripts/r2-audio-smoke.py --seconds 12 --pause-for 2
python3 scripts/r2-audio-smoke.py --seconds 20 --stall-ms 500
python3 scripts/r2-failure-smoke.py
python3 scripts/r2-audio-smoke.py --seconds 8 --close-active
python3 scripts/r2-audio-smoke.py --seconds 3600
python3 scripts/r2-audio-smoke.py --seconds 3600 --validate-only artifacts/r2/ID

dotnet tools/EliteRec.Recorder/bin/Release/net10.0/EliteRec.Recorder.dll \
  --replay tests/EliteRec.Core.Tests/Fixtures/delayed-delivery.json
```

WAV-файлы не перезаписываются. При контролируемой ошибке они финализируются;
восстановление после принудительного убийства/потери питания пока отсутствует.
Smoke-скрипты создают свои null-sink, подают в них одинаковые звуковые маркеры,
сверяют длительности/заголовки/сдвиг каналов и удаляют тестовые устройства.
Длинный прогон использует отдельную неизменяемую копию сборки в `artifacts/`.
Проверка маркеров определяет начало импульса с разрешением в один отсчёт
(1/48000 с); первые/последние 2 с исключаются из сравнения, поскольку граница
записи может обрезать импульс. `--validate-only` повторяет проверку готовых WAV.
Хеши продуктовых библиотек в прогоне совпадают с текущей сборкой:
[tested-libraries.json](r2-results/tested-libraries.json).
Файлы WAV остаются локально в `artifacts/r2/`, в репозиторий не добавляются.

## Источники API

- [PulseAudio stream API](https://www.freedesktop.org/software/pulseaudio/doxygen/stream_8h.html) —
  захват, время/задержки, различие сглаженного и raw timing.
- [pa_timing_info](https://www.freedesktop.org/software/pulseaudio/doxygen/structpa__timing__info.html) —
  индексы, метка измерения и задержки источника/монитора.
